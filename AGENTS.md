# Dictum

`AGENTS.md` is part of this repository's source code and should evolve with the package. Update it when the project design, MCP tool contracts, or file layout changes meaningfully. In particular, consider updating the file index when adding, moving, or removing a file. Routine work does not require editing this document.

## 1. Project overview

Dictum is a local project-management MCP server for coding agents. Its goal is to let any working agent understand a project, execute a well-defined task, and resume previous work using durable records instead of the original conversation. The agent performs research, external tool calls, implementation, and verification; Dictum manages context, relationships, progress, and accepted decisions.

The MVP uses Rust, `rmcp`, stdio, and one SQLite database containing multiple projects per server process. Multiple local clients must point to the same database to share project state. `DICTUM_DATABASE` selects its path; the default is `.dictum/dictum.sqlite3` relative to the process working directory. Stdout is reserved for MCP; diagnostics go to stderr.

The binary also serves a localhost dashboard, `dictum-mcp dashboard --port 3000`, as a sibling transport over the same Store and database. The React 19 + TanStack Query UI uses shadcn/ui-style components and Tailwind CSS v4. Accessible One-time and Recurring tabs keep tasks primary, and project Decisions and Sources follow the task board without requiring a task selection. Its production assets are embedded in the binary; normal use needs no frontend dev server, CDN, external fonts, or remote services. The dashboard binds only `127.0.0.1`, exposes GET JSON reads (projects, tasks, context, result pages, decisions, sources, runs) plus narrowly scoped run launch/cancel POSTs, never edits records or executes source actions, rejects foreign Host and Origin values, requires a per-service request token for mutations, and serves a restrictive content policy. The dashboard process is the single run supervisor for its database: it spawns temporary Codex/Claude subprocesses, records durable attempts distinct from task results, and enforces one active run per task and per canonical working directory. MCP clients and the dashboard can run concurrently and restart independently.

`WORKFLOW.md` is the canonical, compact agent workflow (at most 2,000 characters). It is embedded in the binary and delivered through MCP server instructions, not a separate tool or required skill installation. Put task-authoring and authorization rules first. The human and agent coauthor the actual task content, not a separate approval brief; preserve agreed intent, constraints, required approach, and acceptance criteria. Once authorized, one coordinator can derive inspectable tasks, delegate bounded work, obtain separate reviews, and record evidence. These are agent guidance, not server-enforced approval or orchestration. Clients control instruction inclusion, retention, and subagent inheritance; actual CLI behavior needs separate validation.

The model has twelve tables: `projects`, `tasks`, `sources`, `decisions`, `task_context_sources`, `task_dependencies`, `task_results`, `task_result_sources`, `task_feedback`, `task_feedback_addresses`, `task_runs`, and `service_lock`. `service_lock` holds run-service ownership, not project data.

- **Projects:** a name, description, immutable server-assigned UUIDv7 ID, and UTC `created_at`. Names need not be unique. Every task, source, decision, relationship, dependency and supersession belongs to exactly one project. Require an existing `project_id` on all task/source/decision tools and reject cross-project references atomically. Discover with `list_projects` before `list_tasks(project_id, ready_to_start=true)` and `get_task_context(project_id, task_id)`; resolve ambiguity or no match with the human rather than implicitly creating or selecting a project. Scope does not grant execution authorization or claim work.

- **Tasks:** a title, required Markdown sections for problem/goal and design, acceptance criteria, and optional rejected alternatives. Keep this execution brief separate from status and progress. Immutable `kind` defaults to `one_time`, with `todo`, `in_progress`, `blocked`, and `done` statuses; `done` requires every dependency gate to be done, at least one successful execution result, and no outstanding `changes_requested` feedback. `recurring` tasks reuse the same ID, brief and context sources and use `active` (default) or `paused`. Active describes eligibility for externally authorized work, not a running invocation or installed schedule. Only recurring tasks accept an optional nonblank `trigger_event` label; it is external event metadata, not a subscription or wakeup guarantee. `ready_to_start` remains a one-time todo query; discover recurrence explicitly by kind/status.
- **Execution results:** append-only `task_results` entries retain every success, no_change or failure and per-entry output Source IDs in `task_result_sources`. Each entry stores nonblank reported evidence (at most 4,000 characters), server UTC `recorded_at` (not execution observation time), and the resulting task revision. Append and same-project output associations are atomic under `expected_revision`. Both kinds may append; no append changes lifecycle. A paused task can record already-performed work without reactivation. No-change counts as successful; failures preserve earlier successes. Source identities remain associated, but their contents retain the mutable-source contract. No automatic deletion, per-run task, exactly-once execution or claim mechanism exists.
- **Result feedback:** append-only `task_feedback` entries target one result on the same task/project. Store nonblank Markdown `body` (max 4,000 characters), disposition `comment` (default) or `changes_requested`, server UTC `recorded_at`, and resulting task revision. Record under `expected_revision`; a change request atomically reopens a done one-time task to todo, while other statuses and recurring active/paused are preserved. A success/no_change result may explicitly address outstanding feedback through `addressed_feedback_ids`; `task_feedback_addresses` retains each link exactly once. Failures cannot address feedback. Task edits and new attempts never implicitly clear it. Addressing is reported remediation, not human acceptance; another review can request further changes. Comments do not block done. No authenticated reviewer identity or mandatory approval workflow exists.
- **Runs:** `task_runs` stores durable one-shot dashboard attempts separately from `task_results`: project/task identity, agent, reported version and executable, canonical working directory, input task revision, status (`running`, `succeeded`, `failed`, `cancelled`, `timed_out`, `interrupted`), start/end, exit code, stop reason, cancellation request, process ID, bounded raw log and extracted progress; raw logs are fetched by the UI only while expanded. Partial unique indexes allow only one running attempt per task and per canonical working directory. `service_lock` gives one dashboard process ownership of runs for a database; a new service claims only after the prior owner PID is gone or positively identified as a zombie; unavailable process inspection does not permit takeover. Restart cleanup signals only process groups verified against the canonical database path and persisted attempt identity, then marks leftover running rows interrupted. Unverifiable processes are not signalled. Launch eligibility requires satisfied before-start gates and a one-time `todo`/`in_progress`/`blocked` or recurring `active` task; `done` and `paused` tasks are rejected, and before-done remains a completion gate. Launch validates an absolute existing directory and a version-checked Codex/Claude executable, returns a run ID immediately, and enforces a bounded timeout (default 30 minutes; `DICTUM_RUN_TIMEOUT_SECONDS`). Codex runs with `--ignore-user-config` and Claude Code with `--strict-mcp-config`, so each attempt receives only its run-scoped Dictum MCP configuration; explicit model overrides use `DICTUM_CODEX_MODEL`/`DICTUM_CLAUDE_MODEL`. Cancellation, timeout, abnormal exit and service restart terminate or mark the process group where possible. A `dictum-mcp` process started with `DICTUM_RUN_ID` is run-scoped: the value must be a positive integer or startup fails, it may read context and call `record_task_result`, which links at most one result to that run, and every other mutating tool is rejected. The agent process inherits no `DICTUM_*` variables; database and run identity are supplied only by its run-scoped MCP configuration. A successful process exit never changes task lifecycle, and no scheduler, automatic launch or retry exists.
- **Task relationships:** sources are linked many-to-many to tasks as `context`; outputs are associated with individual execution results, not task-level links. Dependencies have kind `before_start` or `before_done`, each requiring the referenced task to be done. Targets must be one_time tasks, because recurring tasks never reach done. Reject self-links and cycles across both kinds. Recurring tasks may depend on ordinary tasks. Appending success/no_change requires both start and completion gates satisfied for either kind; failure reports are allowed with unmet gates. Starting ordinary work and satisfying completion gates remain separate; dependencies never automatically complete work. A test result must identify what was tested and the outcome; the agent determines whether evidence applies to the final implementation.
- **Sources:** a name, a short description explaining contents and relevance, and exactly one of inline `content` or an external `locator`. `context_policy` is `always` or `when_relevant`. An optional `action` contains an `instruction` and a `manual` or `interval` trigger. Context inclusion and action scheduling are independent.
- **Source state:** retain one successful `snapshot` and one `latest_attempt` on the source, without a check-history table. A snapshot contains `observed_at`, a short current `summary`, optional opaque `checkpoint`, and supporting `references`. Target one to three sentences and enforce at most 1,000 characters for summaries. Successful no-change results advance freshness while retaining the brief; failures retain the entire last successful snapshot. Only completing the configured action advances its freshness/checkpoint; a targeted lookup for one task does not. Changing the content, locator, or action invalidates state produced under the old definition.
- **Context retrieval:** return full, untruncated inline documents. External sources return their locator, action, snapshot, latest attempt, and computed due information. Task context includes that project's current decisions and deduplicated context-linked plus `always` sources. Execution history is bounded to `latest_result` and `latest_successful_result`; matching IDs identify the same entry. Independently, `outstanding_feedback` includes every unaddressed comment/change request together with its original full result, even outside bounded history. Results include all their feedback and `addressed_feedback_ids`; addressing state is derived at read time. This intentionally keeps outstanding review context visible across attempts. Historical output IDs appear on those entries. Retrieve older full entries via `list_task_results`, newest IDs first, default page size 20 (1..100). `next_before_id` continues with older IDs; cursors must exist in the same task/project. Concurrent appends do not alter subsequent page membership; feedback annotations reflect the current read snapshot. Expand source content with `get_source`. Reading never records execution or advances freshness.
- **Decisions:** accepted project-wide choices, distinct from sources. Store statement, rationale, optional nullable Markdown `alternatives_rejected`, and server-assigned UTC `created_at`. Omitted or null alternatives store NULL; empty text is allowed, matching task alternatives. Decisions are immutable: preserve an earlier choice by creating a replacement with `supersedes_id`, which carries its own alternatives without changing the predecessor. Current decisions have no successor, and a current decision can have only one replacement.

Use transactions, foreign keys, and optimistic revision checks for mutable task/source records. Derive readiness and freshness instead of maintaining duplicate flags. Keep the MVP free of hosting, built-in connectors, background scheduling, automatic agent launching, generic workflow engines, and separate handoff/artifact models. A document produced by a task becomes an ordinary Source linked with role `output`.

## 2. Tools supported

Optional update fields preserve their existing values when omitted. Explicit null clears nullable fields (task alternatives/progress/trigger_event, source content/locator/action, and no-change checkpoint). Supplied relationship arrays replace that set atomically; an empty array clears it. Mutable updates require `expected_revision` from the latest read.

| Tool | Parameters and purpose |
| --- | --- |
| `create_project` | Required `name` and `description`. Create a project with a server-assigned UUIDv7 ID and creation time; names need not be unique. |
| `list_projects` | Optional `query` over names/descriptions. Discover projects before selecting an explicit scope. |
| `create_task` | Required `title`, `problem_or_goal`, `design`, `acceptance_criteria`; optional `kind` (default one_time), recurring-only `trigger_event`, `alternatives_rejected`, `context_source_ids`, `prerequisite_task_ids`, `completion_task_ids`. Create the brief and relationships together. |
| `list_tasks` | Optional `kind`, `status`, exact `trigger_event`, `ready_to_start`, and `query` filters. Discover tasks and unmet dependencies; recurring tasks are never ready_to_start. |
| `get_task_context` | `task_id`. Read the complete task brief, progress, dependency state, current decisions, expanded context sources, bounded latest result history, and all outstanding feedback with its original result. |
| `update_task` | `task_id`, `expected_revision`, and optional brief, kind-specific `status`, `progress`, recurring `trigger_event`, context/dependency IDs. `done` requires satisfied gates, at least one successful result, and no outstanding change requests. Brief edits preserve feedback. Kind is immutable. |
| `record_task_result` | `task_id`, `expected_revision`, `outcome` (success/no_change/failure), nonblank `evidence` (max 4,000 characters), optional `output_source_ids` and `addressed_feedback_ids`. Success/no_change may explicitly address outstanding feedback on this task; failure may not. Append evidence and associations atomically; increment revision without changing lifecycle. This is the only task result/output write path. |
| `record_task_feedback` | `task_id`, `result_id`, `expected_revision`, nonblank `body` (max 4,000 characters), optional `disposition` (`comment` default or `changes_requested`). Append feedback and increment task revision atomically; change requests reopen done one-time tasks to todo. |
| `list_task_results` | `task_id`, optional `page_size` (default 20, 1..100) and `before_id`. Return newest-first `results` and `next_before_id` for stable older-history pagination. |
| `create_source` | `name`, `description`, exactly one of `content`/`locator`; optional `context_policy` and `action`. Register reusable project information; external registration does not create the external resource. |
| `list_sources` | Optional `task_id`, `representation` (`inline`/`external`), `action_due`, and `query` filters. Discover compact source descriptors; task filtering uses explicit links. |
| `get_source` | `source_id`. Expand a source to its complete inline content or external reference and current action state. |
| `update_source` | `source_id`, `expected_revision`, and optional definition changes. Correct content, location, description, context policy, or action. |
| `record_source_action` | `source_id`, `expected_revision`, and `result`: success with observation time/brief/checkpoint/references, no-change with observation time and optional checkpoint, or failure with an error. Atomically retain the latest outcome and successful snapshot. |
| `record_decision` | `statement`, `rationale`, optional nullable Markdown `alternatives_rejected`, optional `supersedes_id`. Record an immutable accepted choice with its creation time, optionally replacing a current choice. Omitted or null alternatives store NULL; empty text is allowed. |
| `list_decisions` | Optional `include_superseded`; default false. Read current decisions or their retained history, including each decision's own `alternatives_rejected`. Task context exposes the same field on current decisions. |

All fourteen task/source/decision/feedback tools require `project_id`; the two project tools do not. Task, task-summary, task-result, task-feedback, source, source-descriptor and decision results include `project_id`. Project lists return `projects`, each with `id`, `name`, `description`, and `created_at`. Unknown project IDs and records outside the supplied project are errors. Project scoping is data isolation, not authorization or a claim. Inline content and task sections are Markdown. Source action intervals use positive `every_minutes`; no successful snapshot means immediately due. Manual actions have no automatic due time. Tool descriptions and results distinguish reported verification from independently executed tests. Task filtering in `list_sources` covers context links; retrieve output associations via `list_task_results`. No MCP tool starts or cancels a run; those controls are dashboard-only HTTP routes. A server process launched with `DICTUM_RUN_ID` is run-scoped: reads and `record_task_result` are allowed, while `create_project`, `create_task`, `update_task`, `record_task_feedback`, `create_source`, `update_source`, `record_source_action`, and `record_decision` are rejected so task authoring, status, review and other project records stay with the user.

Build with `cargo build --locked`; launch `target/debug/dictum-mcp` through an MCP client with `DICTUM_DATABASE` set to an absolute shared path. Launch the dashboard with `DICTUM_DATABASE=/abs/path target/debug/dictum-mcp dashboard --port 3000` (port `0` selects a free port); it reports the actual URL and database path on stderr. Run one dashboard per database: it owns the run service lease and rejects a second owner. Runs use `codex` and `claude` from `PATH` unless `DICTUM_CODEX_BIN`/`DICTUM_CLAUDE_BIN` override them; `DICTUM_CODEX_MODEL`/`DICTUM_CLAUDE_MODEL` pass an explicit model when needed. Minimum validated versions are Codex 0.100.0 and Claude Code 2.1.285, and `DICTUM_RUN_TIMEOUT_SECONDS` overrides the 30-minute limit. The committed `web/dist` bundle lets `cargo build --locked` work without Node; after changing frontend sources, run `(cd web && npm ci && npm run build)` and commit the refreshed bundle. Verify with `cargo fmt --check`, `cargo test --locked`, and `cargo clippy --locked --all-targets -- -D warnings`. Only schema v9 is supported; startup rejects older schemas without modifying them. Preserve an older database and choose a fresh path such as `.dictum/dictum-v9.sqlite3`; re-create needed records through MCP rather than migrating the file.

## 4. Rules

- End-to-end tests only. No unit tests. Exercise the real processes through MCP stdio and, for dashboard changes, the real HTTP listener against the same SQLite database, including persistence; do not test internal functions or the store API directly. Database setup/inspection is allowed for test fixtures and persistence assertions. UI behavior needs a real browser check in addition to HTTP assertions.
