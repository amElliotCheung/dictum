# Dictum

`AGENTS.md` is part of this repository's source code and should evolve with the package. Update it when the project design, MCP tool contracts, or file layout changes meaningfully. In particular, consider updating the file index when adding, moving, or removing a file. Routine work does not require editing this document.

## 1. Project overview

Dictum is a source of truth for product intent, evolution, and future direction. It complements the agent's harness; it does not replace it.

Dictum is a local project-management MCP server for coding agents. Its goal is to let any working agent understand a project, execute a well-defined task, and resume previous work using durable records instead of the original conversation. The agent performs research, external tool calls, implementation, and verification; Dictum manages context, relationships, progress, and accepted decisions.

The MVP uses Rust, `rmcp`, stdio, and one SQLite database containing multiple projects per server process. Multiple local clients must point to the same database to share project state. `DICTUM_DATABASE` selects its path; the default is `.dictum/dictum.sqlite3` relative to the process working directory. Stdout is reserved for MCP; diagnostics go to stderr.

The binary also serves a localhost dashboard, `dictum-mcp dashboard --port 3000`, as a sibling transport over the same Store and database. The React 19 + TanStack Query UI uses shadcn/ui-style components and Tailwind CSS v4. Accessible One-time and Recurring tabs keep tasks primary, and project Decisions and Sources follow the task board without requiring a task selection. A project topic filter applies to tasks and the project Decisions and Sources sections. Its production assets are embedded in the binary; normal use needs no frontend dev server, CDN, external fonts, or remote services. The dashboard binds only `127.0.0.1`, exposes GET JSON reads (projects, tasks, context, comment pages, decisions and sources) plus scoped comment POSTs, rejects other writes and foreign Host and Origin values, and serves a restrictive content policy. Comment POSTs require an allowed Origin, JSON bodies bounded to 64 KiB, and a random per-dashboard request token returned by `/api/request-token`. Tokens change on process restart. MCP clients and dashboards can run concurrently and restart independently.

`WORKFLOW.md` is the canonical, compact agent workflow (at most 2,000 characters). It is embedded in the binary and delivered through MCP server instructions, not a separate tool or required skill installation. Put task-authoring and authorization rules first. The human and agent coauthor the actual task content, not a separate approval brief; preserve agreed intent, constraints, required approach, and acceptance criteria. Once authorized, one coordinator can derive inspectable tasks, delegate bounded work, obtain separate reviews, and record evidence. These are agent guidance, not server-enforced approval or orchestration. Clients control instruction inclusion, retention, and subagent inheritance; actual CLI behavior needs separate validation.

All project, topic, task, source, decision and comment identities and references use canonical lowercase, hyphenated UUIDv7 strings through the shared Rust `Id` type. Numeric and non-v7 inputs are rejected at MCP and HTTP boundaries; SQLite identity constraints enforce the same format. SQLite has no built-in UUIDv7 function, so `src/id.rs::new_id` serves every entity. Call it under an immediate write transaction; it compares the candidate against the largest persisted UUID across all identity tables and increments the UUIDv7 suffix when needed, preserving append order across processes, restarts and clock regressions. Dashboard request tokens are independent random secrets, not entity IDs.

The model has twelve tables: `projects`, `topics`, `tasks`, `sources`, `decisions`, `task_topics`, `source_topics`, `decision_topics`, `task_context_sources`, `task_dependencies`, `task_comments`, and `task_comment_sources`.

- **Projects:** a name, description, immutable server-assigned UUIDv7 ID, revision starting at 1, and UTC `created_at`/`updated_at` (equal at creation). Names need not be unique. `update_project` replaces only the nonblank description under `expected_revision`; each accepted update, including identical text, increments revision and sets server UTC `updated_at`. ID, name, creation time and related records are preserved. Every task, source, decision, relationship, dependency and supersession belongs to exactly one project. Require an existing `project_id` on all context/task/source/decision tools and reject cross-project references atomically. Discover with unpaginated `list_projects`; resolve ambiguity or no match with the human rather than implicitly creating or selecting a project. Read `get_context(project_id)` for project orientation, or `list_tasks(project_id, ready_to_start=true)` then `get_context(project_id, task_id)` for a task. Scope does not grant execution authorization or claim work.

- **Topics:** project-local entities with immutable server-assigned UUIDv7 `id`, `project_id`, and a specific `name`, typically tens per project. Every project response includes its complete `topics` directory, including currently unused topics; adding topics does not advance the project's description revision or timestamps. Every task, source and decision has at least one topic, with many-to-many membership. Required nonempty `topics` name arrays on `create_task`, `create_source`, and `record_decision` resolve or create topics atomically with the record. Optional `topics` on task/source updates replaces membership; omission preserves it, while null, empty arrays, and blank names are errors. Normalize whitespace and case for exact reuse, preserve the first collapsed display spelling, and deduplicate repeated names. Reuse a matching concept in `project.topics` before creating another name; prefer `user authentication` or a more specific name over `authentication`. Semantic specificity is agent guidance, not server classification or fuzzy merging. `list_tasks`, `list_sources`, and `list_decisions` accept an optional exact normalized topic name; unknown names return no matches, blank names fail, and reads never create topics. Topics support discovery without automatic context expansion, source inheritance, hierarchy, scheduling or authorization. No dedicated topic tool exists. Decision memberships are immutable; each replacement supplies its own topics explicitly.

- **Tasks:** a title, required Markdown sections for problem/goal and design, acceptance criteria, and optional rejected alternatives. Both kinds have `priority` (`low`, `medium`, or `high`), defaulting to `medium`; priority is ordering metadata and does not change lifecycle or dependency gates. Keep this execution brief separate from status and progress. Immutable `kind` defaults to `one_time`, with `todo`, `in_progress`, `blocked`, and `done` statuses; `done` requires every dependency gate to be done and at least one historical success/no-change execution comment. Only `update_task` advances task revision and `updated_at`; each accepted edit, including status, progress, priority, or relationship changes, creates another task version. Comments do not change the task record. `recurring` tasks reuse the same ID, brief and context sources and use `active` (default) or `paused`. Active describes eligibility for externally authorized work, not a running invocation or installed schedule. Only recurring tasks accept an optional nonblank `trigger_event` label; it is external event metadata, not a subscription or wakeup guarantee. `ready_to_start` remains a one-time todo query; discover recurrence explicitly by kind/status.
- **Subtasks:** nullable `parent_task_id` attaches a task to one root in the same project and of the same immutable kind. One-time and recurring parentage cannot cross. Only one level is supported: reject self-parenting, a parent that is itself a subtask, and making a task with children into a subtask. Create defaults remain unchanged; recurring children explicitly use `kind=recurring`. Validate and write under one immediate transaction, including concurrent reparenting/creation. Parentage is organizational: no implicit dependencies, lifecycle, priority, topic/source inheritance, execution permission, or completion rollup. The parent and child briefs complement one another; put shared goals, constraints, and approach in the parent and specific work/criteria in the child, avoid repetition, and read both. Context includes the full `parent_task` or null, without recursively expanding its sources/history.
- **Comments and execution reports:** immutable `task_comments` retain required nonblank Markdown `body` (at most 4,000 characters), server UTC `recorded_at`, required target `task_revision`, optional same-task `reply_to_comment_id`, and optional `execution_result` containing outcome success/no_change/failure and output Source IDs. The body supplies execution evidence. Targets are 1 through the task's current revision, including earlier versions; many comments may target the same version. No author, disposition, addressing, or outstanding-feedback fields exist. Appends and same-project outputs are atomic and change neither task revision nor task update time or lifecycle. Rework uses discussion and explicit task/status updates, without automatic reopening. Source identities persist while contents remain mutable. A paused recurring task may record already-performed execution. Versions identify task records; old brief bodies and parent/source snapshots are not retained. No automatic deletion, exactly-once execution, or claim mechanism exists.
- **Task relationships:** sources are linked many-to-many to tasks as `context`; outputs are associated with individual execution comments, not task-level links. Dependencies have kind `before_start` or `before_done`, each requiring the referenced task to be done. Targets must be one_time tasks, because recurring tasks never reach done. Reject self-links and cycles across both kinds. Recurring tasks may depend on ordinary tasks. Appending an execution comment with success/no_change requires both start and completion gates satisfied for either kind; failure reports are allowed with unmet gates. Starting ordinary work and satisfying completion gates remain separate; dependencies never automatically complete work. A test result must identify what was tested and the outcome; the agent determines whether evidence applies to the final implementation.
- **Sources:** a name, a short description explaining contents and relevance, and exactly one of inline `content` or an external `locator`. `context_policy` is `always` or `when_relevant`. Use a concise inline `always` Source for environment facts needed across tasks: environment scope, exact account/region/resource identifiers, and verification references or dates where useful. Facts describe current state; decisions describe accepted choices, which may not yet be implemented. Update facts when reality changes; keep project descriptions focused on purpose and scope. An optional `action` contains an `instruction` and a `manual` or `interval` trigger. Context inclusion and action scheduling are independent.
- **Source state:** retain one successful `snapshot` and one `latest_attempt` on the source, without a check-history table. A snapshot contains `observed_at`, a short current `summary`, optional opaque `checkpoint`, and supporting `references`. Target one to three sentences and enforce at most 1,000 characters for summaries. Successful no-change results advance freshness while retaining the brief; failures retain the entire last successful snapshot. Only completing the configured action advances its freshness/checkpoint; a targeted lookup for one task does not. Changing the content, locator, or action invalidates state produced under the old definition.
- **Context retrieval:** `get_context` requires `project_id` and accepts optional `task_id`, replacing `get_task_context`. Both modes return the full project and all current decisions in ascending ID order, including rationale and alternatives, in one consistent database read snapshot. Without a task, include all `always` Sources; `task`, `parent_task`, and `dependency_state` are null, `recent_comments` is empty, and `latest_execution` and `latest_successful_execution` are null. With a task, include its full brief, full parent task or null, dependency state, and deduplicated explicit context-linked plus `always` Sources. Inline documents remain full and untruncated; external sources return their locator, action, snapshot, latest attempt, and due information. Context Sources and decisions are unpaginated. Task comments remain bounded to ten newest `recent_comments`, `latest_execution`, and `latest_successful_execution` (success/no_change); matching IDs identify the same entry, without deduplicating the response. Read older entries with `list_task_comments`, newest first, default page size 20 (1..100); optional `has_execution_result` filters plain or execution comments. `next_before_id` continues older history; cursors must belong to the same task/project. Concurrent appends preserve subsequent page membership. Fetch one full flat entry with `get_task_comment`, and expand output Source IDs with `get_source`. Reading does not record execution or advance freshness. Comment polling is independent of task revisions. Historical success remains completion evidence; the agent/human determines whether it applies to the final implementation.
- **Source and decision discovery:** `list_sources` and `list_decisions` accept `page_size` (default 20, range 1..100) and optional `before_id`, returning newest IDs first and `next_before_id`. A cursor must be a UUIDv7 ID of an existing record of the listed kind in the same project; validate it independently of filters. Apply filters before page limiting and look ahead for an older matching record; only then return the last returned record's ID as `next_before_id`, otherwise null. Source listings remain compact descriptors; decision listings remain full records. Later appends have higher IDs and do not enter older pages, but source edits, action freshness, and decision supersession can change data or filter membership between reads. `list_projects` remains unpaginated.
- **Decisions:** accepted project-wide choices, distinct from sources. Store statement, rationale, optional nullable Markdown `alternatives_rejected`, and server-assigned UTC `created_at`. Omitted or null alternatives store NULL; empty text is allowed, matching task alternatives. Decisions are immutable: preserve an earlier choice by creating a replacement with `supersedes_id`, which carries its own alternatives without changing the predecessor. Current decisions have no successor, and a current decision can have only one replacement. Every returned decision includes server-derived `current_decision_id`, identifying the current end of its project-local chain at read time (its own ID when current), including outside a requested history page. Derive this field within the same read snapshot, without a stored pointer or schema change. Stale replacements fail with the current ID and require rereading; never redirect writes automatically. Reversals create new immutable records with complete current statements and rationales; do not reactivate earlier records or infer semantic equivalence between independent chains.

Write comments and execution reports for later agents, normally in 1–3 short sentences or bullets. Preserve useful findings, corrections, blockers, next steps, and evidence; skip narration, duplicate information, and polling that adds no useful information. Execution evidence identifies what was done or checked, the implementation or artifact tested, the outcome, and relevant remaining limitations. Task versions identify briefs, not code revisions. Fresh verification can warrant a `no_change` report. Preserve explicit reporting requirements and completion evidence. Use output Sources for longer durable artifacts when needed; do not create a Source for every note.

Start with bounded task context and fetch older comments only for a specific gap, using small pages (for example `page_size: 5`), filters, or direct comment IDs. Stop when the gap is resolved; avoid routine full-history scans. Expand only needed output Sources and poll comments independently of task revisions, without reloading full context solely for comments. Source listings return descriptors, not automatic context inclusion. Every linked and `always` inline Source is returned in full by task-scoped `get_context`; project-only context includes all `always` Sources. Keep always Sources small and link only needed task context. These authoring and retrieval guidelines do not change limits or full-source inclusion.

Use transactions, foreign keys, and optimistic revision checks for mutable project/task/source records. Derive readiness and freshness instead of maintaining duplicate flags. Keep the MVP free of hosting, built-in connectors, background scheduling, automatic agent launching, generic workflow engines, and separate handoff/artifact models. A document produced by a task becomes an ordinary Source linked with role `output`.

## 2. Tools supported

Optional update fields preserve their existing values when omitted. Explicit null clears nullable fields (task parent/alternatives/progress/trigger_event, source content/locator/action, and no-change checkpoint). Supplied relationship arrays replace that set atomically; an empty array clears it, except `topics`, which must remain nonempty and rejects null. Mutable updates require `expected_revision` from the latest read.

| Tool | Parameters and purpose |
| --- | --- |
| `create_project` | Required `name` and `description`. Create a project with a server-assigned UUIDv7 ID, revision 1 and equal UTC creation/update times; names need not be unique. |
| `list_projects` | Optional `query` over names/descriptions. Discover projects before selecting an explicit scope. Results remain unpaginated. |
| `update_project` | Required existing `project_id`, latest `expected_revision`, and nonblank `description`. Replace only the description atomically, increment revision and set server UTC `updated_at`, including for identical text. Null and unknown fields are rejected; revision conflicts leave data unchanged. |
| `create_task` | Required `title`, `problem_or_goal`, `design`, `acceptance_criteria`, and nonempty `topics` names; optional same-kind root `parent_task_id`, `kind` (one_time default), `priority` (medium default), recurring-only `trigger_event`, `alternatives_rejected`, context and dependency IDs. Create brief/topics/relationships atomically; parent and child briefs complement each other. |
| `list_tasks` | Optional kind/status/priority/trigger_event/readiness/query and exact normalized `topic` name filters; `parent_task_id` omitted lists all, null lists roots, ID lists direct children. A supplied ID must exist in the project; filtering by a child yields no descendants. Preserve priority then ID ordering; summaries include topics. |
| `get_context` | Required `project_id`, optional `task_id`. Full project with its complete topic directory and all current full decisions in either mode. Without a task: always Sources, null task/parent/dependency state, empty recent comments and null latest execution/success. With a task: full brief and parent, progress, dependency state, full own context plus always Sources, ten recent comments and bounded latest execution/success. One consistent read snapshot; no automatic topic expansion, recursive parent context or feedback state. |
| `update_task` | `task_id`, `expected_revision`, optional brief, priority, status, progress, recurring trigger, nonempty replacement `topics` names, context/dependencies, and nullable parent patch. Every accepted update increments version/time; done requires dependency gates and at least one historical success/no-change execution. Kind is immutable. |
| `record_task_comment` | `task_id`, target `task_revision` (1..current), nonblank `body` (max 4,000 characters), optional same-task `reply_to_comment_id` and `execution_result` with outcome and optional output Source IDs. No `expected_revision`: append preserves task version/time/status. Success/no-change checks current dependency gates; failure may report unmet gates. |
| `list_task_comments` | `task_id`, optional `page_size` (20 default, 1..100), `before_id`, and `has_execution_result`. Return newest-first `comments` and `next_before_id` for stable older-history pagination. |
| `get_task_comment` | `task_id`, `comment_id`. Retrieve one full immutable comment within the explicit task/project scope. |
| `create_source` | `name`, `description`, nonempty `topics` names, exactly one of `content`/`locator`; optional `context_policy` and `action`. Register reusable project information and topic links atomically; external registration does not create the external resource. |
| `list_sources` | Optional `task_id`, `representation` (`inline`/`external`), `action_due`, `query`, and exact normalized `topic` name filters; `page_size` (20 default, 1..100), and same-project UUIDv7 `before_id`. Return newest-first compact `sources` descriptors with topics and filtered `next_before_id`; task filtering uses explicit links. Validate cursors independently of filters. |
| `get_source` | `source_id`. Expand a source to its complete inline content or external reference and current action state. |
| `update_source` | `source_id`, `expected_revision`, and optional definition changes or nonempty replacement `topics` names. Topic edits preserve source action state. |
| `record_source_action` | `source_id`, `expected_revision`, and `result`: success with observation time/brief/checkpoint/references, no-change with observation time and optional checkpoint, or failure with an error. Atomically retain the latest outcome and successful snapshot. |
| `record_decision` | `statement`, `rationale`, nonempty `topics` names, optional nullable Markdown `alternatives_rejected`, optional `supersedes_id`. Record an immutable accepted choice and topic links with its creation time and server-derived `current_decision_id`, optionally replacing a current choice. Each replacement explicitly supplies topics. Omitted or null alternatives store NULL; empty text is allowed. Reject stale replacements with their current decision ID so the agent can reread. |
| `list_decisions` | Optional `include_superseded` (false default), exact normalized `topic` name, `page_size` (20 default, 1..100), and same-project UUIDv7 `before_id`. Return newest-first full `decisions` with topics and filtered `next_before_id`; validate cursors independently of filters. Read current choices or retained history, including each decision's own `alternatives_rejected` and server-derived `current_decision_id` across the full chain, even outside this page. Context still includes all current decisions in full. |

All tools except `create_project` and `list_projects` require `project_id`. There are still seventeen tools; `get_context` replaces `get_task_context`, and topics add no tool. Task, task-summary, task-comment, source, source-descriptor and decision results include `project_id`. Tasks, task summaries, Sources, Source descriptors and decisions include `topics`, an array of full `{id, project_id, name}` objects. Project lists return `projects`, each with `id`, `name`, `description`, `topics`, `revision`, `created_at`, and `updated_at`; project creation, updates, and the context `project` field use the same shape. New projects have an empty topic directory. Unknown project IDs and records outside the supplied project are errors. Project scoping is data isolation, not authorization or a claim. Inline content and task sections are Markdown. Source action intervals use positive `every_minutes`; no successful snapshot means immediately due. Manual actions have no automatic due time. Tool descriptions and results distinguish reported verification from independently executed tests. Task filtering in `list_sources` covers context links; retrieve output associations via `list_task_comments`.

The dashboard exposes project-only context at `GET /api/projects/:id/context` and task context at `GET /api/projects/:id/tasks/:task_id`. Project `/tasks`, `/decisions`, and `/sources` reads accept a `topic` name; `/decisions` and `/sources` also accept `page_size` and `before_id` and return the same paginated result shapes as MCP. Topic filtering composes with existing filters before pagination. The Decisions and Sources sections load further pages with **Load more**. UUIDv7 identities require the twelve-table v15 schema; older schemas are rejected without migration.

## 4. Rules

- End-to-end tests only. No unit tests. Exercise the real processes through MCP stdio and, for dashboard changes, the real HTTP listener against the same SQLite database, including persistence; do not test internal functions or the store API directly. Database setup/inspection is allowed for test fixtures and persistence assertions. UI behavior needs a real browser check in addition to HTTP assertions.
