# Dictum

`AGENTS.md` is part of this repository's source code and should evolve with the package. Update it when the project design, MCP tool contracts, or file layout changes meaningfully. In particular, consider updating the file index when adding, moving, or removing a file. Routine work does not require editing this document.

## 1. Project overview

Dictum is a source of truth for product intent, evolution, and future direction. It complements the agent's harness; it does not replace it.

Dictum is a local project-management MCP server for coding agents. Its goal is to let any working agent understand a project, execute a well-defined task, and resume previous work using durable records instead of the original conversation. The agent performs research, external tool calls, implementation, and verification; Dictum manages context, relationships, progress, and accepted decisions.

The MVP uses Rust, `rmcp`, stdio, and one SQLite database containing multiple projects per server process. Multiple local clients must point to the same database to share project state. `DICTUM_DATABASE` selects its path; the default is `.dictum/dictum.sqlite3` relative to the process working directory. Stdout is reserved for MCP; diagnostics go to stderr.

The binary also serves a localhost dashboard, `dictum-mcp dashboard --port 3000`, as a sibling transport over the same Store and database. The React 19 + TanStack Query UI uses shadcn/ui-style components and Tailwind CSS v4. Accessible One-time and Recurring tabs keep tasks primary, and project Decisions and Sources follow the task board without requiring a task selection. Its production assets are embedded in the binary; normal use needs no frontend dev server, CDN, external fonts, or remote services. The dashboard binds only `127.0.0.1`, exposes GET JSON reads (projects, tasks, context, comment pages, decisions and sources) plus scoped comment POSTs, rejects other writes and foreign Host and Origin values, and serves a restrictive content policy. Comment POSTs require an allowed Origin, JSON bodies bounded to 64 KiB, and a random per-dashboard request token returned by `/api/request-token`. Tokens change on process restart. MCP clients and dashboards can run concurrently and restart independently.

`WORKFLOW.md` is the canonical, compact agent workflow (at most 2,000 characters). It is embedded in the binary and delivered through MCP server instructions, not a separate tool or required skill installation. Put task-authoring and authorization rules first. The human and agent coauthor the actual task content, not a separate approval brief; preserve agreed intent, constraints, required approach, and acceptance criteria. Once authorized, one coordinator can derive inspectable tasks, delegate bounded work, obtain separate reviews, and record evidence. These are agent guidance, not server-enforced approval or orchestration. Clients control instruction inclusion, retention, and subagent inheritance; actual CLI behavior needs separate validation.

The model has eight tables: `projects`, `tasks`, `sources`, `decisions`, `task_context_sources`, `task_dependencies`, `task_comments`, and `task_comment_sources`.

- **Projects:** a name, description, immutable server-assigned UUIDv7 ID, revision starting at 1, and UTC `created_at`/`updated_at` (equal at creation). Names need not be unique. `update_project` replaces only the nonblank description under `expected_revision`; each accepted update, including identical text, increments revision and sets server UTC `updated_at`. ID, name, creation time and related records are preserved. Every task, source, decision, relationship, dependency and supersession belongs to exactly one project. Require an existing `project_id` on all task/source/decision tools and reject cross-project references atomically. Discover with `list_projects` before `list_tasks(project_id, ready_to_start=true)` and `get_task_context(project_id, task_id)`; resolve ambiguity or no match with the human rather than implicitly creating or selecting a project. Scope does not grant execution authorization or claim work.

- **Tasks:** a title, required Markdown sections for problem/goal and design, acceptance criteria, and optional rejected alternatives. Both kinds have `priority` (`low`, `medium`, or `high`), defaulting to `medium`; priority is ordering metadata and does not change lifecycle or dependency gates. Keep this execution brief separate from status and progress. Immutable `kind` defaults to `one_time`, with `todo`, `in_progress`, `blocked`, and `done` statuses; `done` requires every dependency gate to be done and at least one historical success/no-change execution comment. Only `update_task` advances task revision and `updated_at`; each accepted edit, including status, progress, priority, or relationship changes, creates another task version. Comments do not change the task record. `recurring` tasks reuse the same ID, brief and context sources and use `active` (default) or `paused`. Active describes eligibility for externally authorized work, not a running invocation or installed schedule. Only recurring tasks accept an optional nonblank `trigger_event` label; it is external event metadata, not a subscription or wakeup guarantee. `ready_to_start` remains a one-time todo query; discover recurrence explicitly by kind/status.
- **Subtasks:** nullable `parent_task_id` attaches a task to one root in the same project and of the same immutable kind. One-time and recurring parentage cannot cross. Only one level is supported: reject self-parenting, a parent that is itself a subtask, and making a task with children into a subtask. Create defaults remain unchanged; recurring children explicitly use `kind=recurring`. Validate and write under one immediate transaction, including concurrent reparenting/creation. Parentage is organizational: no implicit dependencies, lifecycle, priority, source inheritance, execution permission, or completion rollup. The parent and child briefs complement one another; put shared goals, constraints, and approach in the parent and specific work/criteria in the child, avoid repetition, and read both. Task summaries remain unchanged. Context includes the full `parent_task` or null, without recursively expanding its sources/history.
- **Comments and execution reports:** immutable `task_comments` retain required nonblank Markdown `body` (at most 4,000 characters), server UTC `recorded_at`, required target `task_revision`, optional same-task `reply_to_comment_id`, and optional `execution_result` containing outcome success/no_change/failure and output Source IDs. The body supplies execution evidence. Targets are 1 through the task's current revision, including earlier versions; many comments may target the same version. No author, disposition, addressing, or outstanding-feedback fields exist. Appends and same-project outputs are atomic and change neither task revision nor task update time or lifecycle. Rework uses discussion and explicit task/status updates, without automatic reopening. Source identities persist while contents remain mutable. A paused recurring task may record already-performed execution. Versions identify task records; old brief bodies and parent/source snapshots are not retained. No automatic deletion, exactly-once execution, or claim mechanism exists.
- **Task relationships:** sources are linked many-to-many to tasks as `context`; outputs are associated with individual execution comments, not task-level links. Dependencies have kind `before_start` or `before_done`, each requiring the referenced task to be done. Targets must be one_time tasks, because recurring tasks never reach done. Reject self-links and cycles across both kinds. Recurring tasks may depend on ordinary tasks. Appending an execution comment with success/no_change requires both start and completion gates satisfied for either kind; failure reports are allowed with unmet gates. Starting ordinary work and satisfying completion gates remain separate; dependencies never automatically complete work. A test result must identify what was tested and the outcome; the agent determines whether evidence applies to the final implementation.
- **Sources:** a name, a short description explaining contents and relevance, and exactly one of inline `content` or an external `locator`. `context_policy` is `always` or `when_relevant`. An optional `action` contains an `instruction` and a `manual` or `interval` trigger. Context inclusion and action scheduling are independent.
- **Source state:** retain one successful `snapshot` and one `latest_attempt` on the source, without a check-history table. A snapshot contains `observed_at`, a short current `summary`, optional opaque `checkpoint`, and supporting `references`. Target one to three sentences and enforce at most 1,000 characters for summaries. Successful no-change results advance freshness while retaining the brief; failures retain the entire last successful snapshot. Only completing the configured action advances its freshness/checkpoint; a targeted lookup for one task does not. Changing the content, locator, or action invalidates state produced under the old definition.
- **Context retrieval:** return full, untruncated inline documents. External sources return their locator, action, snapshot, latest attempt, and due information. Task context includes its project's current decisions, full parent task or null, and deduplicated explicit context-linked plus `always` sources. Comments are bounded to ten newest `recent_comments`, `latest_execution`, and `latest_successful_execution` (success/no_change); matching IDs identify the same entry. Read older entries with `list_task_comments`, newest first, default page size 20 (1..100); optional `has_execution_result` filters plain or execution comments. `next_before_id` continues older history; cursors must belong to the same task/project. Concurrent appends preserve subsequent page membership. Fetch one full flat entry with `get_task_comment`, and expand output Source IDs with `get_source`. Reading does not record execution or advance freshness. Comment polling is independent of task revisions. Historical success remains completion evidence; the agent/human determines whether it applies to the final implementation.
- **Decisions:** accepted project-wide choices, distinct from sources. Store statement, rationale, optional nullable Markdown `alternatives_rejected`, and server-assigned UTC `created_at`. Omitted or null alternatives store NULL; empty text is allowed, matching task alternatives. Decisions are immutable: preserve an earlier choice by creating a replacement with `supersedes_id`, which carries its own alternatives without changing the predecessor. Current decisions have no successor, and a current decision can have only one replacement.

Use transactions, foreign keys, and optimistic revision checks for mutable project/task/source records. Derive readiness and freshness instead of maintaining duplicate flags. Keep the MVP free of hosting, built-in connectors, background scheduling, automatic agent launching, generic workflow engines, and separate handoff/artifact models. A document produced by a task becomes an ordinary Source linked with role `output`.

## 2. Tools supported

Optional update fields preserve their existing values when omitted. Explicit null clears nullable fields (task parent/alternatives/progress/trigger_event, source content/locator/action, and no-change checkpoint). Supplied relationship arrays replace that set atomically; an empty array clears it. Mutable updates require `expected_revision` from the latest read.

| Tool | Parameters and purpose |
| --- | --- |
| `create_project` | Required `name` and `description`. Create a project with a server-assigned UUIDv7 ID, revision 1 and equal UTC creation/update times; names need not be unique. |
| `list_projects` | Optional `query` over names/descriptions. Discover projects before selecting an explicit scope. |
| `update_project` | Required existing `project_id`, latest `expected_revision`, and nonblank `description`. Replace only the description atomically, increment revision and set server UTC `updated_at`, including for identical text. Null and unknown fields are rejected; revision conflicts leave data unchanged. |
| `create_task` | Required `title`, `problem_or_goal`, `design`, `acceptance_criteria`; optional same-kind root `parent_task_id`, `kind` (one_time default), `priority` (medium default), recurring-only `trigger_event`, `alternatives_rejected`, context and dependency IDs. Create brief/relationships atomically; parent and child briefs complement each other. |
| `list_tasks` | Optional kind/status/priority/trigger_event/readiness/query filters; `parent_task_id` omitted lists all, null lists roots, ID lists direct children. A supplied ID must exist in the project; filtering by a child yields no descendants. Preserve priority then ID ordering and existing summary fields. |
| `get_task_context` | `task_id`. Full brief and parent task, progress, dependency state, decisions, expanded own context sources, ten recent comments and bounded latest execution/success. No recursive parent context or feedback state. |
| `update_task` | `task_id`, `expected_revision`, optional brief, priority, status, progress, recurring trigger, context/dependencies, and nullable parent patch. Every accepted update increments version/time; done requires dependency gates and at least one historical success/no-change execution. Kind is immutable. |
| `record_task_comment` | `task_id`, target `task_revision` (1..current), nonblank `body` (max 4,000 characters), optional same-task `reply_to_comment_id` and `execution_result` with outcome and optional output Source IDs. No `expected_revision`: append preserves task version/time/status. Success/no-change checks current dependency gates; failure may report unmet gates. |
| `list_task_comments` | `task_id`, optional `page_size` (20 default, 1..100), `before_id`, and `has_execution_result`. Return newest-first `comments` and `next_before_id` for stable older-history pagination. |
| `get_task_comment` | `task_id`, `comment_id`. Retrieve one full immutable comment within the explicit task/project scope. |
| `create_source` | `name`, `description`, exactly one of `content`/`locator`; optional `context_policy` and `action`. Register reusable project information; external registration does not create the external resource. |
| `list_sources` | Optional `task_id`, `representation` (`inline`/`external`), `action_due`, and `query` filters. Discover compact source descriptors; task filtering uses explicit links. |
| `get_source` | `source_id`. Expand a source to its complete inline content or external reference and current action state. |
| `update_source` | `source_id`, `expected_revision`, and optional definition changes. Correct content, location, description, context policy, or action. |
| `record_source_action` | `source_id`, `expected_revision`, and `result`: success with observation time/brief/checkpoint/references, no-change with observation time and optional checkpoint, or failure with an error. Atomically retain the latest outcome and successful snapshot. |
| `record_decision` | `statement`, `rationale`, optional nullable Markdown `alternatives_rejected`, optional `supersedes_id`. Record an immutable accepted choice with its creation time, optionally replacing a current choice. Omitted or null alternatives store NULL; empty text is allowed. |
| `list_decisions` | Optional `include_superseded`; default false. Read current decisions or their retained history, including each decision's own `alternatives_rejected`. Task context exposes the same field on current decisions. |

All fourteen task/source/decision/comment tools and `update_project` require `project_id`; `create_project` and `list_projects` do not. Task, task-summary, task-comment, source, source-descriptor and decision results include `project_id`. Project lists return `projects`, each with `id`, `name`, `description`, `revision`, `created_at`, and `updated_at`; project creation and updates return the same shape. Unknown project IDs and records outside the supplied project are errors. Project scoping is data isolation, not authorization or a claim. Inline content and task sections are Markdown. Source action intervals use positive `every_minutes`; no successful snapshot means immediately due. Manual actions have no automatic due time. Tool descriptions and results distinguish reported verification from independently executed tests. Task filtering in `list_sources` covers context links; retrieve output associations via `list_task_comments`.

Build with `cargo build --locked`; launch `target/debug/dictum-mcp` through an MCP client with `DICTUM_DATABASE` set to an absolute shared path. Launch the dashboard with `DICTUM_DATABASE=/abs/path target/debug/dictum-mcp dashboard --port 3000` (port `0` selects a free port); it reports the actual URL and database path on stderr. The committed `web/dist` bundle lets `cargo build --locked` work without Node; after changing frontend sources, run `(cd web && npm ci && npm run build)` and commit the refreshed bundle. Verify with `cargo fmt --check`, `cargo test --locked`, and `cargo clippy --locked --all-targets -- -D warnings`. Only schema v13 is supported; startup rejects older schemas without modifying them. Preserve an older database and choose a fresh path such as `.dictum/dictum-v13.sqlite3`; re-create needed records through MCP rather than migrating the file.

## 4. Rules

- End-to-end tests only. No unit tests. Exercise the real processes through MCP stdio and, for dashboard changes, the real HTTP listener against the same SQLite database, including persistence; do not test internal functions or the store API directly. Database setup/inspection is allowed for test fixtures and persistence assertions. UI behavior needs a real browser check in addition to HTTP assertions.
